# Handling HTTP 429 & Retry-After Header in Java

Как правильно обрабатывать ошибку HTTP 429 Too Many Requests и заголовок Retry-After при интеграции с LLM API на Java?

---ANSWER---

### Короткий ответ
При получении HTTP 429 необходимо проверить заголовок Retry-After (в секундах или HTTP-дате). Если заголовок присутствует, поток ожидает указанное время перед повтором. Если заголовка нет, применяется экспоненциальный backoff с jitter. При превышении лимита повторов выбрасывается контролируемое исключение для пользователя.

### Подробное объяснение
Провайдеры LLM применяют два типа лимитов:
- **RPM (Requests Per Minute)**: лимит числа запросов.
- **TPM (Tokens Per Minute)**: лимит суммарного объема токенов.

При превышении любого из них возвращается HTTP 429.

### Алгоритм обработки в Java:
1. Проверить статус ответа statusCode == 429.
2. Извлечь заголовок Retry-After:
   - Если число: Duration.ofSeconds(Long.parseLong(val))
   - Если дата: распарсить через DateTimeFormatter.RFC_1123_DATE_TIME и вычислить дельту до Instant.now().
3. Ограничить максимальное время ожидания (например, не ждать более 15 секунд в синхронном потоке пользователя).
4. Если заголовок отсутствует, использовать экспоненциальный интервал: delay = initialDelay * (2 ^ attempt) + randomJitter.

### Пример метода извлечения задержки:
```java
public Duration extractRetryDelay(HttpResponse<?> response, int attempt) {
    Optional<String> retryAfterHeader = response.headers().firstValue("Retry-After");
    if (retryAfterHeader.isPresent()) {
        try {
            long seconds = Long.parseLong(retryAfterHeader.get().trim());
            return Duration.ofSeconds(Math.min(seconds, 30));
        } catch (NumberFormatException e) {
            ZonedDateTime retryDate = ZonedDateTime.parse(retryAfterHeader.get(), DateTimeFormatter.RFC_1123_DATE_TIME);
            long secs = Duration.between(Instant.now(), retryDate.toInstant()).toSeconds();
            return Duration.ofSeconds(Math.max(1, Math.min(secs, 30)));
        }
    }
    // Fallback: Exponential backoff + jitter
    long baseBackoffMs = 1000L * (1L << attempt);
    long jitter = ThreadLocalRandom.current().nextLong(100, 500);
    return Duration.ofMillis(baseBackoffMs + jitter);
}
```

### Уточняющий вопрос на интервью (Follow-up)
Почему ожидание Thread.sleep более 5-10 секунд в классическом веб-потоке Tomcat (до виртуальных потоков Java 21) может положить весь сервер?

### Распространённый неверный ответ (Pitfall)
При 429 мгновенно повторять запрос в цикле while(true), что приводит к бану API-ключа провайдером и исчерпанию пула потоков Tomcat.

### Key Points
- HTTP 429 сигнализирует об исчерпании RPM или TPM квоты.
- Заголовок Retry-After имеет приоритет над алгоритмами локального бэкоффа.
- Обязателен верхний порог ожидания (cap) для защиты времени отклика пользователя.
- Добавление случайного jitter предотвращает Thundering Herd (эффект толпы).

### Life Analogy
Если кассир говорит: 'Очередь перегружена, отойдите на 10 секунд' (Retry-After), не нужно каждую миллисекунду дергать ручку кассы — отойдите ровно на 10 секунд.
