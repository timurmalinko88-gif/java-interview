# Structured Output vs Free-Form Text: Limits & Semantics

Как работает механизм Structured Output (JSON Schema / JSON Mode) в LLM API? Почему синтаксически валидный JSON не гарантирует семантическую корректность данных для Java-бэкенда?

---ANSWER---

### Короткий ответ
Structured Output накладывает грамматический парсер (constrained decoding) на генерацию токенов, гарантируя 100% соответствие синтаксиса JSON Schema. Однако модель всё ещё способна генерировать семантические галлюцинации (несуществующие ID, отрицательные цены, вымышленные статусы), поэтому валидация Java Bean Validation (JSR-380) строго обязательна.

### Подробное объяснение
При интеграции LLM в бизнес-логику свободный текст неудобен. Провайдеры предлагают механизмы принудительного формата:
1. **JSON Mode (type: json_object)**: модель проинструктирована вернуть JSON, но схема не форсируется жестко. Возможны отсутствующие поля и синтаксические сбои при нехватке токенов.
2. **Strict Structured Output (response_format с strict: true и JSON Schema)**: на этапе инференса применяется маскирование логитов (logit bias / grammar masking). Модель физически не может сгенерировать токен, нарушающий грамматику указанной JSON Schema.

### Проблема: Синтаксис vs Семантика
Structured Output решает проблему JsonParseException, но НЕ решает проблему бизнес-корректности:
- Модель вернет {"ticketId": 999999}, которого нет в БД.
- Модель вернет {"status": "REFUNDED"}, хотя платеж не проводился.
- Модель вернет математически неверную сумму позиций в чеке.

### Правильный подход в Java:
```java
public record TicketDto(
    @NotNull @Positive Long ticketId,
    @NotBlank @Size(max = 100) String category,
    @Pattern(regexp = "OPEN|IN_PROGRESS|CLOSED") String status,
    @Min(1) @Max(5) int priority
) {}

// Обязательная валидация после десериализации!
Set<ConstraintViolation<TicketDto>> violations = validator.validate(ticketDto);
if (!violations.isEmpty()) {
    throw new InvalidLlmPayloadException("Модель вернула семантически невалидные поля");
}
```

### Уточняющий вопрос на интервью (Follow-up)
Как вы поступите, если модель вернула валидный JSON, но поле ID сущности отсутствует в вашей PostgreSQL базе?

### Распространённый неверный ответ (Pitfall)
Считать, что флаг strict: true заменяет валидацию бизнес-логики и проверку наличия сущностей в БД.

### Key Points
- Strict Structured Output гарантирует только совпадение схемы и типов данных.
- Constrained decoding предотвращает синтаксические сбои, но не галлюцинации.
- Java Bean Validation и проверка существования сущностей в БД обязательны.
- Для enum значений всегда проверяйте допустимый allowlist в Java коде.

### Life Analogy
Structured Output гарантирует, что вам прислали заполненную налоговую декларацию строгой формы без клякс и с цифрами в нужных графах. Но если заявитель написал в графе 'доход' миллион рублей вместо десяти — форма правильная, а данные ложные.
