# Complete 6-Step Lifecycle of LLM Tool Calling in Java

Опишите полный 6-шаговый жизненный цикл выполнения Tool / Function Calling между Java-бэкендом и LLM. Какова точная роль модели на каждом этапе?

---ANSWER---

### Короткий ответ
1. Backend отправляет в API модель, сообщения и JSON Schema инструментов. 2. Модель решает вызвать функцию и возвращает tool_calls с именем и JSON-аргументами (stop_reason='tool_calls'). 3. Backend парсит аргументы, валидирует схему и проверяет права доступа. 4. Backend локально вызывает Java-метод. 5. Backend возвращает результат модели отдельным сообщением с ролью tool и тем же tool_call_id. 6. Модель формирует финальный ответ или запрашивает следующий инструмент.

### Подробное объяснение
Фундаментальный принцип: **LLM сама не имеет доступа к вашей ОС, JVM, базе данных или сети**. Она лишь преобразует текст в текст и запрашивает вызов функции согласно предоставленному контракту.

### 6 шагов взаимодействия:
```
[User Browser] -> 1. Prompt -> [Java Backend] -> 1. Tools Schema + Messages -> [LLM API]
                               [Java Backend] <- 2. tool_call (name, args) <-  [LLM API]
                               [Java Backend] validates args & user RBAC
                               [Java Backend] executes local Java service method
                               [Java Backend] -> 5. tool result (tool_call_id) -> [LLM API]
[User Browser] <- 6. Response <- [Java Backend] <- 6. Final text response <- [LLM API]
```

1. **Инициализация**: Java отправляет историю диалога + массив tools: [{type: "function", function: {name, description, parameters: JSONSchema}}].
2. **Запрос вызова от LLM**: Если модели нужны внешние данные, она прекращает генерацию обычного текста и возвращает структуру:
   tool_calls: [{id: "call_abc123", type: "function", function: {name: "getServiceStatus", arguments: "{\"serviceName\":\"payment\"}"}}].
3. **Контроль и валидация на Backend**: Java-бэкенд сопоставляет name с белым списком разрешенных бинов, десериализует JSON-аргументы и проверяет права текущего пользователя на запуск этой операции.
4. **Исполнение**: Backend выполняет бизнес-метод (serviceStatusService.checkStatus("payment")).
5. **Возврат контекста**: Backend отправляет ВСЮ предыдущую историю + сообщение ассистента с tool_calls + новое сообщение:
   {"role": "tool", "tool_call_id": "call_abc123", "content": "{\"status\": \"UP\", \"latency\": 12}"}.
6. **Синтез ответа**: Модель получает сырые данные от инструмента и генерирует связный ответ для пользователя на естественном языке.

### Уточняющий вопрос на интервью (Follow-up)
Что произойдет, если на шаге 5 в сообщении с ролью tool отправить неверный или отсутствующий tool_call_id?

### Распространённый неверный ответ (Pitfall)
Думать, что модель 'сама дергает метод в Java' через рефлексию или удаленный вызов, и забывать передавать tool_call_id при отправке результата.

### Key Points
- Модель генерирует только намерение вызова функции и JSON-аргументы.
- Выполнение кода происходит исключительно на вашем Java-бэкенде.
- Обязательно соответствие каждого tool result уникальному tool_call_id.
- Бэкенд обязан валидировать имя функции и аргументы перед запуском.

### Life Analogy
Архитектор (LLM) чертит на бумаге план: 'выкопать траншею глубиной 2 метра' (tool_call). Рабочий с лопатой (Java backend) читает чертеж, проверяет разрешение на земляные работы, копает траншею и докладывает архитектору: 'Траншея выкопана, внутри глина' (tool result). Архитектор на основе этого решает, какой фундамент закладывать дальше.
