# Idempotency & Two-Phase Confirmation for Mutating Tools

Как проектировать изменяющие состояние (mutating) Tools? Зачем нужны ключи идемпотентности и двухфазное подтверждение человеком (Human-in-the-Loop)?

---ANSWER---

### Короткий ответ
Изменяющие инструменты (оплата, удаление данных, отправка email) несут риск случайного или повторного выполнения из-за сетевых retry или галлюцинаций модели. Они требуют: 1) двухфазного подтверждения (сначала генерация драфта операции, затем подтверждение человеком через UI), 2) ключей идемпотентности (Idempotency Key) для предотвращения дублирующих списаний.

### Подробное объяснение
Разница между Read-Only и Mutating инструментами колоссальна:
- Read-Only (getServiceStatus, searchArticles): безопасны для автоматического вызова в цикле.
- Mutating (transferMoney, cancelSubscription, deleteServer): автоматический вызов моделью без участия человека в production недопустим.

### Двухфазный паттерн Human-in-the-Loop:
1. **Фаза 1 (Proposal)**: Модель вызывает инструмент proposeTicketCancellation(ticketId, reason).
   - Метод не отменяет тикет сразу! Он создает черновик операции в Redis со статусом PENDING и коротким TTL (5 минут) и возвращает actionConfirmationToken: "act_777".
   - Модель отвечает пользователю: "Я подготовил отмену тикета #101. Подтвердите действие".
2. **Фаза 2 (Confirmation)**: Пользователь нажимает кнопку в UI сайта [Подтвердить отмену], которая отправляет прямой POST-запрос с токеном act_777 на защищенный endpoint /api/operations/confirm.

### Идемпотентность (Idempotency):
```java
public OrderResult executeOrderCreation(CreateOrderArgs args, String idempotencyKey) {
    return idempotencyRepository.findById(idempotencyKey)
        .map(OrderResult::alreadyProcessed)
        .orElseGet(() -> {
            Order order = orderService.create(args);
            idempotencyRepository.save(idempotencyKey, order);
            return OrderResult.created(order);
        });
}
```

### Уточняющий вопрос на интервью (Follow-up)
Почему retry на уровне HTTP-клиента к LLM может привести к двойному списанию средств, если mutating-метод был вызван моделью на первом шаге?

### Распространённый неверный ответ (Pitfall)
Давать модели инструмент с прямым вызовом деструктивной операции в базе данных без подтверждения реальным пользователем.

### Key Points
- Мутирующие инструменты должны быть разделены на подготовку (draft) и подтверждение.
- Критичные действия требуют обязательного одобрения человеком (Human-in-the-Loop).
- Идемпотентность защищает от дублирования операций при сбоях сети и повторах.
- Никогда не выполняйте необратимые действия в автоматическом цикле агента.

### Life Analogy
В интернет-банке вы сначала заполняете реквизиты перевода, а затем банк присылает вам СМС-код с подтверждением суммы и получателя. Ни один банк не списывает деньги автоматически по первому намёку.
