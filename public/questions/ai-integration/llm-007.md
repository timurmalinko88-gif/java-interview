# Retry Strategies & Non-Retryable LLM Errors

Какие HTTP-ошибки LLM API категорически нельзя повторять через retry, а какие требуют ограниченного повтора? Чем опасен бесконечный retry?

---ANSWER---

### Короткий ответ
Ошибки 400 (Bad Request), 401 (Unauthorized), 403 (Forbidden), 404 (Not Found) и 422 являются невосстанавливаемыми (non-retryable) — повтор запроса гарантированно завершится той же ошибкой. Повторять можно только транзиентные сбои: 429 (с backoff), 500/502/503 (Server Error) и сетевые таймауты. Бесконечный retry приводит к блокировке потоков, падению бэкенда и гигантским финансовым списаниям.

### Подробное объяснение
Классификация ошибок при вызове AI-провайдера:

### 1. Non-Retryable (Немедленный отказ):
- **401 / 403**: Неверный API-ключ, истекшая подписка, отсутствие доступа к модели. Повторные вызовы только заспамят шлюз провайдера.
- **400 Bad Request**: Невалидный JSON, неверные имена параметров, превышение context_window модели. Без изменения тела запроса повтор бесполезен.
- **404 Not Found**: Модель снята с эксплуатации (deprecated) или опечатка в названии model: "gpt-4-typo".

### 2. Retryable (Повторяемые с ограничением попыток, обычно max 3):
- **429 Too Many Requests**: временное превышение лимита RPM/TPM.
- **500 / 502 / 503 / 504**: временная деградация инфраструктуры провайдера (Overloaded).
- **SocketTimeoutException**: сетевой сбой передачи пакетов.

### Чем опасен неконтролируемый retry:
- **Финансовые потери**: если запрос был частично обработан провайдером (например, сбой при чтении стрима), за токены генерации могут списаться деньги при каждом повторе.
- **Каскадный сбой (Cascading Failure)**: накопление заблокированных потоков исчерпывает пул подключений Tomcat/HikariCP.

```java
public boolean isRetryable(int statusCode, Exception ex) {
    if (ex instanceof SocketTimeoutException || ex instanceof IOException) {
        return true;
    }
    return statusCode == 429 || statusCode == 500 || statusCode == 502 || statusCode == 503 || statusCode == 504;
}
```

### Уточняющий вопрос на интервью (Follow-up)
В чем фундаментальное различие между повтором вызова LLM API и повтором бизнес-операции, выполненной инструментом (Tool)?

### Распространённый неверный ответ (Pitfall)
Навешивать @Retryable на весь сервисный метод без фильтрации исключений, повторяя запросы при 401 и 400 ошибках.

### Key Points
- 401, 403, 400 — фатальные ошибки конфигурации и тела запроса, retry запрещен.
- Транзиентные ошибки (429, 503, таймауты) повторяются не более 2-3 раз.
- Обязателен экспоненциальный бэкофф со случайным шумом (Jitter).
- Повтор неидемпотентного запроса к LLM может стоить денег за каждый повтор.

### Life Analogy
Если вы набрали неверный пин-код на терминале (401), бессмысленно повторять операцию бесконечно — карту заблокируют. Но если терминал потерял связь со спутником (503), можно повторить через пару секунд.
