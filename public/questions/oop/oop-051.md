# Static Utility Methods vs Spring Dependency Injection

Why is the widespread use of static utility methods (e.g. `DateHelper`, `SecurityUtils`, `PaymentCalculator`) considered an anti-pattern in modern enterprise Java? How does static coupling violate SOLID principles and hinder unit testing?

---ANSWER---

While `static` methods are standard for pure, stateless functions (such as `Math.max()` or `StringUtils.hasText()`), using static classes for business logic or infrastructure services is a major architectural smell.

### Core Problems with Static Methods in Domain/Business Code

1. **Destroys Unit Testability:**
   - Standard Mockito (`mock()`) cannot mock static methods without bytecode manipulation (`mockStatic()`), which is slow, fragile, and leaks state across test suites.
   - You cannot easily test how a class behaves when a helper throws an exception or returns edge-case values.

2. **Violates Dependency Inversion Principle (DIP):**
   - High-level modules should not depend on low-level concrete implementations; both should depend on abstractions (interfaces).
   - Calling `TokenUtils.verify(token)` hardcodes a compile-time dependency on `TokenUtils`. You cannot swap it for an alternative implementation (e.g. a fake in tests or a different algorithm in production) without changing the calling code.

3. **Hides Dependencies (Inversion of Control Violation):**
   - A class with constructor injection clearly declares its dependencies:
     ```java
     public OrderService(PaymentClient paymentClient, Clock clock) { ... }
     ```
   - If `OrderService` instead invokes `ClockUtil.now()` or `PaymentUtil.charge()`, its dependencies are invisible from its public API, making it unpredictable and prone to hidden side effects.

### When Is `static` Appropriate?
- **Pure Functions:** Functions whose output depends solely on their input parameters, with zero state, zero I/O, and zero side effects (e.g. `Collections.unmodifiableList()`, `Integer.parseInt()`).
- **Static Factory Methods:** E.g., `Optional.of()`, `List.of()`, `UserDto.fromEntity(entity)`.

### Refactoring to Dependency Injection

```java
// ❌ Bad: Static utility with hidden I/O or business logic
public class TokenUtil {
    public static boolean isValid(String token) {
        // Reads secret key, validates signature...
    }
}

// ✅ Good: Spring Service / Component with Interface
public interface TokenValidator {
    boolean isValid(String token);
}

@Service
public class JwtTokenValidator implements TokenValidator {
    @Value("${jwt.secret}")
    private String secret;

    @Override
    public boolean isValid(String token) { ... }
}
```

### Key Takeaways
- Use static methods only for pure mathematical/string transformations with no I/O.
- Any logic that interacts with config, time, random seeds, or external resources should be a Spring `@Component` injected via constructor.\n
